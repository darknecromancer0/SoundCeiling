# SoundCeiling v0.5 Hybrid Engine Design

**Status:** Architecture approved in chat. Implementation remains blocked until this written spec is reviewed.

**Base:** `main` after SoundCeiling v0.4.0.

**Goal:** Evolve SoundCeiling from one mostly stream-level normalizer into a capability-driven Hybrid Engine that preserves the proven v0.4 safety core, adds per-app and system-sound policies, uses PCM intelligently where Android permits it, and never claims source/control/DSP capabilities that are not actually proven.

## 1. Non-negotiable principles

1. **Safety before normalization.** A raise is allowed only when the engine has trustworthy evidence that it is safe and relevant.
2. **No confidence, no raise.** `LIKELY`, `MIXED`, `UNKNOWN`, blocked/uncertain PCM, or unhealthy measurement means automatic upward control is disabled.
3. **Manual user intent outranks automation.** v0.4 manual-pause/effective-envelope behavior stays authoritative.
4. **Safety Lock is final.** Existing `SafetyGuard` and `SafeVolumeController` remain the final ordinary Media write path.
5. **No fake DSP.** Successful PCM capture proves analysis capability, not the ability to replace another app's playback with processed PCM.
6. **Optional subsystems fail closed.** Source identification, OEM integration, DSP and future privileged transports may degrade independently without disabling the core safety guard.
7. **Microphone isolation.** Production analysis must never switch to microphone, call or voice-recording audio sources.
8. **No root requirement for Standard Engine.** Root/Shizuku/OEM privileged paths are future adapters, not v0.5 prerequisites.

## 2. v0.5 scope

### In scope

- Capability model replacing the old single backend tier as the authoritative engine truth.
- Playback activity observation.
- Source identity plus explicit confidence/evidence.
- Optional source-evidence adapters that may use user-granted Android access, but are not required for core safety.
- UID-filtered `AudioPlaybackCapture` when a candidate package UID is known and capture is permitted.
- PCM `IDLE/STARTING/ACTIVE/SILENT_SOURCE/BLOCKED/UNCERTAIN/ERROR` state machine.
- Per-app rules: `GLOBAL`, `ON`, `OFF`, `CUSTOM`.
- App search and app-policy persistence by package name.
- All Samsung/system apps default `OFF` and require explicit user opt-in for app-specific intervention in outgoing sound.
- Separate system-sound policies for Media, Calls, Alarm, Ringtone, Notifications and supported additional streams.
- Calls/Alarm/Ringtone/Notifications default `OFF` independently of app rules.
- Conservative multi-source conflict resolution.
- Device Profiles 2.0 and migration from v0.4 calibration profiles.
- Refactoring `NormalizerService` into a thin lifecycle/orchestration shell.
- Expanded runtime status, diagnostics and black-box events.
- Capability probes for per-app volume and DSP transport.
- UI for Apps & system sounds, Device Profiles 2.0 and engine confidence.

### Explicitly out of scope for Standard Engine v0.5

- Root installation or root-only routing.
- A universal sample-level brickwall limiter for arbitrary third-party playback.
- Guaranteed per-app volume writes on stock Android when no verified control transport exists.
- Automatic UI scripting of Samsung SoundAssistant as a safety-critical mechanism.
- Microphone/call/voice-recording capture or analysis.
- Google Play packaging/policy work.

## 3. Why the architecture changes

`NormalizerService` in v0.4 owns MediaProjection setup, PCM reading, Visualizer fallback, route tracking, settings refresh, control policy, safety application, diagnostics, logging and notification state. v0.5 must not keep adding app/source/device logic into that class.

The foreground service remains the Android lifecycle shell, but it delegates to bounded components. Pure policy components must have no Android writes. Android adapters must expose narrow capability interfaces.

The old `AudioBackendStatus.Tier` may remain temporarily for migration/UI compatibility, but it is no longer the engine's source of truth because metering, source identity, volume control and DSP transport are independent capabilities.

## 4. Capability model

Introduce immutable `EngineCapabilities` with independent dimensions.

### 4.1 Playback observation

`PlaybackObservationCapability`
- `AVAILABLE`
- `DEGRADED`
- `UNAVAILABLE`

Purpose: answer whether playback is believed active and supply independent evidence for PCM-state decisions.

### 4.2 Source identity

`SourceIdentityConfidence`
- `EXACT` — one package/UID is verified strongly enough for source-specific bidirectional control.
- `LIKELY` — one source is plausible but not proven.
- `MIXED` — multiple sources are known or strongly indicated.
- `UNKNOWN` — source cannot be assigned safely.

Only `EXACT` may enable app-specific automatic raise.

### 4.3 Metering

`MeteringCapability`
- `PCM_EXACT` — valid PCM is filtered/verified for the intended exact source.
- `PCM_MIXED` — valid PCM exists but may contain several sources.
- `OUTPUT_MIX_PEAK_RMS` — global Peak/RMS only.
- `ACTIVITY_ONLY` — playback activity without trustworthy level measurement.
- `NONE`.

### 4.4 Volume control

`VolumeControlCapability`
- `PER_APP_VERIFIED`
- `STREAM_MEDIA`
- `SYSTEM_STREAMS`
- `NONE`

Knowing an app UID never implies `PER_APP_VERIFIED`.

### 4.5 DSP transport

`DspTransportCapability`
- `VERIFIED_GLOBAL`
- `VERIFIED_SOURCE`
- `EXPERIMENTAL`
- `UNAVAILABLE`

A successfully constructed Android audio effect or successful PCM capture is insufficient to mark DSP verified.

## 5. Engine components

### 5.1 `PlaybackObserver`

- observes public Android playback activity and usages;
- publishes time-stamped `PlaybackSnapshot` values;
- does not manufacture package/UID identity from weak metadata;
- degrades cleanly when platform metadata is incomplete.

### 5.2 `SourceEvidenceAdapter`

Interface for optional package/source evidence.

Potential Standard Engine adapters may include:
- active media-session package evidence when the user explicitly grants the access required by Android;
- other future public/OEM evidence sources.

Rules:
- optional access is never required for Safety Lock/global fallback;
- media-session/foreground-style evidence alone is at most `LIKELY` unless corroborated;
- adapters must report evidence type and timestamp;
- lack of optional permission produces a normal degraded capability, not an error loop.

### 5.3 `SourceResolver`

Combines:
- `PlaybackSnapshot`;
- optional `SourceEvidenceAdapter` results;
- package-to-UID resolution;
- UID-filtered capture evidence;
- current app policies.

Produces `SourceSet` plus confidence and a reason code.

`EXACT` requires verifiable evidence, for example valid PCM from an `AudioPlaybackCapture` configured for that candidate UID, or a future platform/OEM adapter with equivalent certainty. An active media session by itself is not exact proof that no other app is audible.

Package name is the durable persistence identity. UID is runtime metadata and is refreshed after package changes.

### 5.4 `PcmCaptureBackend`

- owns MediaProjection/AudioPlaybackCapture sessions;
- can construct capture filtered to one or more known candidate UIDs;
- exposes PCM frames, configuration and health;
- never uses microphone/call audio sources;
- never implies DSP write-back.

If no reliable candidate source is available, it may run a permitted mixed/global playback capture for measurement, but that result cannot justify app-specific raise.

### 5.5 `MeteringEngine`

Reuses v0.4:
- `LoudnessMeter`;
- raw block peak calculation;
- `PeakSafetyDetector`;
- `TransientGuard`;
- RMS/LUFS-like tracking;
- frequency diagnostics.

Every `MeasurementSnapshot` carries source confidence and explicit booleans for whether it is trusted for downward control and upward control.

### 5.6 `PcmStateResolver`

Owns the PCM availability state machine and blocked/uncertain logic. It must not equate silence with blocked capture without corroborating playback evidence.

### 5.7 `CapabilityResolver`

Builds `EngineCapabilities` from observer health, source confidence, PCM state, verified control adapters and DSP adapters. Every downgrade exposes a reason suitable for Diagnostics/UI.

### 5.8 `PolicyResolver`

Pure component. Resolves:

`global settings + app rule + device profile + system-stream rule + capabilities -> EffectivePolicy`

It performs no Android writes. It owns conservative multi-source precedence and the `allowAutomaticRaise` decision.

### 5.9 `ControlExecutor`

- ordinary Media writes continue through `SafeVolumeController`;
- system-stream writes go through a separate explicitly enabled adapter;
- unverified per-app adapters may never execute writes;
- rejected/unsupported Android stream writes become a capability downgrade rather than a retry storm.

### 5.10 `DeviceProfileResolver`

Identifies the output route, loads Device Profile 2.0 and supplies calibration/limits/app overrides. Uncertain routes use conservative fallback values.

### 5.11 `DspTransport`

Interface only unless a real transport is verified. Future OEM/Shizuku/root adapters must sit behind it instead of leaking privileged logic into Standard Engine policy code.

## 6. Runtime models

### `PlaybackSnapshot`
Minimum fields:
- `active`
- observed usages/player count
- `updatedElapsedMs`
- observer health

It must not contain a claimed package/UID unless a separate source-evidence path actually supports that claim.

### `SourceDescriptor`
- package name
- runtime UID
- display name
- `systemApp`
- `samsungApp`

### `SourceEvidence`
- evidence type
- package candidate
- runtime UID if known
- timestamp
- strength/reason

### `SourceSet`
- zero/one/many source descriptors
- `SourceIdentityConfidence`
- evidence/reason code

### `MeasurementSnapshot`
- metering capability
- signal present
- raw peak dBFS
- RMS dBFS
- LUFS-like
- transient delta
- source set
- measurement age
- trusted-for-downward
- trusted-for-upward

### `EffectivePolicy`
At minimum:
- control enabled
- allow automatic raise/decrease
- Media min/max
- Safety Lock state/index
- normalization target/preset/strength
- peak/transient thresholds
- active app rule and inheritance source
- device profile key
- fallback ceiling
- system stream + ceiling when resolving a system policy
- explicit block/downgrade reason

## 7. Per-app policy semantics

Each installed app has one persisted rule.

### `GLOBAL`
No special app override. Use current global Media behavior plus active device-profile constraints.

Normal third-party user apps default to `GLOBAL`.

### `ON`
Explicit opt-in. Use global/default control parameters, but record that this app was deliberately enabled. This matters for Samsung/system apps, which otherwise default `OFF`.

### `OFF`
No app-specific normalization/control may be initiated for this app.

If an `OFF` app is part of a mixed source set and only global Media stream control exists, source-specific automatic stream changes that would affect it are blocked. An independently configured global Safety Lock may still clamp Media because that is explicitly global safety behavior.

### `CUSTOM`
May override:
- comfort/target loudness;
- Media ceiling;
- normalization preset/strength;
- source peak threshold;
- transient protection;
- fallback ceiling;
- DSP preference;
- optional per-device overrides.

Custom settings never bypass stricter global/device safety or Safety Lock.

## 8. App discovery, Samsung/system defaults and persistence

- Package name is the stable persistence key.
- UID is resolved on demand and refreshed after install/update/reinstall/package-change events.
- Removed apps keep no active runtime UID.
- Search supports application label and package name.
- UI filters user apps / system apps / Samsung apps.
- **Every app classified as Samsung or Android/system defaults to `OFF`.**
- Changing such an app to `ON` or `CUSTOM` is explicit user permission for SoundCeiling to intervene in its outgoing sound when the engine has a valid control path.
- Ordinary third-party user apps default to `GLOBAL`.
- Classification rules live in one versioned policy/classifier, not scattered UI checks.

This intentionally includes Samsung Gallery and communication/system apps rather than trying to maintain a vague "sensitive only" subset.

## 9. System sounds are a separate policy domain

App opt-in does not opt in Android streams.

Default v0.5 system policy:
- Media: `ON`.
- Calls/Voice call: `OFF`.
- Alarm: `OFF`.
- Ringtone: `OFF`.
- Notifications: `OFF`.
- Other supported system streams: `OFF` unless explicitly enabled.

When a stream is enabled, the user may configure its ceiling. Smart PCM normalization is not assumed for non-Media system streams.

A stream controller must capability-probe real Android behavior. If the OS/device rejects or restricts a requested stream write, SoundCeiling reports that stream as unsupported/degraded and stops attempting unsafe/repetitive writes.

The app-rule toggle for Samsung Clock, Phone, Gallery or another package never silently enables Alarm/Voice-call/Ringtone/Notification stream control.

## 10. PCM availability state machine

`PcmAvailabilityState`
- `IDLE`
- `STARTING`
- `ACTIVE`
- `SILENT_SOURCE`
- `BLOCKED`
- `UNCERTAIN`
- `ERROR`

### `BLOCKED` criterion

`BLOCKED` requires all of:
1. playback activity is currently corroborated;
2. capture was not intentionally stopped by the user;
3. the intended source/usage is eligible for the attempted capture configuration;
4. no valid PCM arrives for a bounded interval;
5. independent evidence indicates audio activity or exact source activity.

Otherwise use `UNCERTAIN`, not `BLOCKED`.

### Safety behavior

- `ACTIVE` + `EXACT` + healthy policy may allow bidirectional normalization.
- `ACTIVE` + `LIKELY/MIXED/UNKNOWN` allows only trusted downward safety and blocks automatic raise.
- `BLOCKED`, `UNCERTAIN` or `ERROR` blocks automatic raise.
- `BLOCKED` may apply an explicitly configured fallback ceiling downward.
- `IDLE` does not chase volume.

## 11. Multi-source conflict resolution

When sources cannot be independently controlled:

1. Global Safety Lock always applies.
2. Any exact `OFF` source blocks source-specific automatic stream changes that would affect it.
3. `LIKELY`, `MIXED` or `UNKNOWN` blocks automatic raise.
4. For downward ceilings, the strictest applicable explicitly enabled safety ceiling wins.
5. App-specific comfort normalization runs only for `EXACT` source identity or verified per-app control isolation.
6. `CUSTOM` may never weaken stricter device/global safety.
7. A source transition resets upward-release timing.
8. If a source disappears and identity becomes uncertain during the transition, the engine remains downward-only until confidence is re-established.

Example: quiet Telegram plus a loud game with only global Media control results in no automatic raise. If both participate and one has a stricter safety ceiling, only the safe downward ceiling may win.

## 12. Device Profiles 2.0

Versioned profile fields:
- stable route/profile key;
- display name;
- Android device type/product metadata;
- calibration offset;
- Media ceiling;
- optional per-system-stream ceilings;
- fallback ceiling for unavailable PCM;
- last selected global control profile;
- per-app override map;
- schema/migration version;
- updated timestamp.

### Migration from v0.4

- preserve every valid calibration offset;
- add missing new fields using conservative defaults;
- migration is idempotent;
- corrupt individual entries are recoverable/skipped without disabling the engine;
- migrated profiles never auto-enable Calls/Alarm/Ringtone/Notifications;
- migrated profiles never convert Samsung/system app rules from default `OFF` to `ON` implicitly.

## 13. Microphone isolation contract

Android may still require `RECORD_AUDIO` permission for playback-analysis APIs, but SoundCeiling production analysis must not capture physical microphone or call/voice sources.

CI/source invariants fail if production engine code introduces:
- `MediaRecorder.AudioSource.MIC`;
- `VOICE_COMMUNICATION`;
- `VOICE_CALL`, uplink/downlink or related call sources;
- `AudioRecord.Builder.setAudioSource(...)` in the playback-analysis path.

`PcmCaptureBackend` uses playback capture configuration only.

Camera, recorder, Telegram/other voice recording and call microphone ownership remain outside SoundCeiling.

## 14. Samsung/OEM and per-app control

- Samsung/system app intervention is opt-in at app-policy level.
- Outgoing playback is the only intended target of an opted-in app rule.
- No OEM/UI automation is considered safety-critical unless programmatically verified.
- SoundAssistant UI automation is not part of Standard Engine.
- `PerAppVolumeController` starts as an interface plus `Unsupported` stock implementation.
- A future OEM adapter reports `PER_APP_VERIFIED` only after a real device capability probe succeeds.

## 15. DSP architecture

### Standard Engine v0.5

Keeps v0.4 stream-level safety/normalization and reports DSP capability truthfully.

UI may say:
- DSP unavailable;
- DSP experimental;
- DSP verified for this source/output.

EQ/compressor/limiter must not claim global third-party protection unless a verified `DspTransport` actually controls that output scope.

### Future Deep DSP Engine

When a privileged/OEM transport can really intercept and replace output, intended processing order is:

`input PCM -> normalization gain -> EQ -> multiband compressor -> look-ahead peak stage -> true-peak/brickwall limiter -> output`

Future root/Shizuku/OEM implementations consume the same policy/device/app models behind adapters.

## 16. UI

Add **Apps & system sounds**.

### Apps
- search label/package;
- filters for user/system/Samsung;
- each app shows `Global`, `On`, `Off`, or `Custom`;
- Samsung/system apps visibly begin `Off` and require opt-in;
- Custom opens app-specific settings;
- optional device override is visibly separate from global app settings.

### System sounds
Separate rows for Media, Calls, Alarm, Ringtone, Notifications and supported additional streams. Non-Media rows begin disabled and reveal a ceiling only when enabled.

### Engine status
Simple mode uses compact states such as:
- `Smart PCM`;
- `PCM blocked - safe fallback`;
- `Mixed apps - raise paused`;
- `Source uncertain - raise paused`;
- `Waiting for audio`;
- `Safe fallback`;
- `System limiter only`;
- `DSP active` only when verified.

Advanced/Diagnostics shows independent capability dimensions, source confidence/evidence and downgrade reasons.

Optional source-detection permissions must be explained as enhancements. Declining them must leave global safety fully usable.

## 17. Diagnostics and black-box logging

Keep the v0.4 bounded log budget and never record PCM.

New events:
- playback activity start/stop;
- source-confidence/evidence transitions;
- package/UID refresh;
- PCM-state transitions;
- capability upgrades/downgrades;
- app/system policy resolution;
- multi-source conflicts;
- system-stream write capability/failure;
- device profile migration/switch;
- unsupported per-app/DSP adapter attempts;
- every automatic-raise block reason.

Suggested codes:
- `source_unknown`
- `source_likely`
- `source_mixed`
- `pcm_blocked`
- `pcm_uncertain`
- `per_app_control_unavailable`
- `dsp_transport_unverified`
- `system_stream_disabled`
- `system_stream_unavailable`
- `policy_conflict_off_source`
- `device_profile_fallback`
- `raise_blocked_confidence`

Stable repeated states are deduplicated.

## 18. Safety/control precedence

For ordinary Media:

1. manual user intent/manual pause;
2. explicit `OFF` constraints relevant to the audible source set;
3. capability/source-confidence no-raise gate;
4. emergency raw-peak/transient downward request;
5. loudness normalization request;
6. strictest app/device/global ceiling;
7. Safety Lock;
8. `SafeVolumeController -> VolumeApplier`.

No new component may call `AudioManager.setStreamVolume(STREAM_MUSIC, ...)` directly.

System-stream writes are separate and limited to an explicitly enabled stream policy plus a verified/working adapter.

## 19. Backward compatibility

- v0.4 Simple/Advanced settings remain readable.
- manual-pause behavior remains.
- Safety Lock remains final and default-off.
- LUFS-like/peak/transient logic is reused rather than rewritten unless tests require a change.
- log retention remains bounded.
- calibration offsets survive Device Profile 2.0 migration.
- MediaProjection remains the precision PCM entry point.

## 20. Testing and release gates

### Pure tests
Must cover:
- capability combinations;
- exact/likely/mixed/unknown confidence;
- no auto-raise for likely/mixed/unknown/blocked/uncertain/error;
- evidence upgrades/downgrades;
- app rule defaults/inheritance/custom overrides;
- every Samsung/system app classification defaulting to `OFF`;
- `OFF` source conflicts;
- strictest-ceiling resolution;
- source-transition upward hold;
- system streams default-off except Media;
- system-stream unsupported/degraded result handling;
- Device Profile 2.0 migration/idempotence;
- UID refresh after package change;
- fallback ceiling behavior;
- verified vs unverified DSP/per-app control.

### Source invariants
CI rejects:
- ordinary Media write callers outside approved writer path;
- microphone/call audio sources in production analysis;
- direct `PER_APP_VERIFIED`/verified-DSP claims outside capability adapters;
- automatic-raise paths bypassing confidence/policy gate;
- app-rule code that defaults Samsung/system packages to anything other than `OFF`;
- non-Media system policy defaulting enabled.

### Android/integration checks
Where practical:
- package list/search/persistence;
- package UID resolution and refresh;
- UID-filtered capture configuration construction;
- optional source-evidence adapter permission/degraded states;
- system-stream mapping/defaults;
- route/profile switching and migration;
- runtime-state rendering.

### Regression gates
All v0.4 pure/source/UI/package contracts remain green unless intentionally versioned with an equivalent stronger replacement.

### Release acceptance
v0.5 may merge only when:
1. Standard Engine works without root.
2. new app/device logic cannot bypass core Media SafetyGuard.
3. automatic raise is impossible for `LIKELY`, `MIXED`, `UNKNOWN`, `BLOCKED`, `UNCERTAIN` or unhealthy measurement.
4. Calls/Alarm/Ringtone/Notifications remain default `OFF`.
5. every Samsung/system app remains app-policy `OFF` until explicit opt-in.
6. package name, not permanent UID, is persistence identity.
7. Device Profile 2.0 migration preserves v0.4 calibration.
8. production analysis has no microphone/call audio source.
9. unsupported per-app/DSP/system-stream capabilities are reported unavailable/degraded rather than simulated.
10. all v0.4 and v0.5 gates pass.
11. `assembleDebug`, artifact checksum and immutable-head/tree verification pass before merge.

## 21. Implementation boundary

The first v0.5 release is deliberately separable from future privileged DSP work.

Expected layers:
1. pure capability/source/evidence/policy models;
2. app classifier/discovery/persistence;
3. system-stream policy model;
4. Device Profiles 2.0 migration;
5. playback observer and optional source-evidence adapters;
6. PCM state resolver and UID-filtered capture infrastructure;
7. conservative multi-source resolver;
8. refactored service orchestration;
9. Apps & system sounds / device-profile UI;
10. diagnostics and release gates.

Future Deep DSP transports are separate follow-up projects behind the interfaces defined here.

## 22. Android API reality assumptions

The implementation must preserve these conservative assumptions unless later platform research proves a stronger device/version-specific adapter:

- Android playback configuration can reveal activity/audio attributes but must not be assumed to reveal another app's UID/package through public APIs.
- `AudioPlaybackCaptureConfiguration.Builder.addMatchingUid(uid)` can filter capture to a known UID, and successful valid PCM from that targeted capture can serve as strong source evidence.
- active media-session package information requires privileged media-control access or an enabled notification-listener path; it is optional evidence, not a core requirement.
- playback capture availability does not mean every third-party playback is capturable.
- PCM analysis does not itself provide an output-replacement transport.
- global/per-app DSP status reflects verified transport scope, not successful effect construction alone.

When a stronger Android/OEM capability is discovered, add a new adapter and capability proof rather than weakening the baseline safety rules.
