# SoundCeiling v0.5 Hybrid Engine Design

**Status:** Design approved in chat; implementation is intentionally blocked until this written spec is reviewed.

**Base:** `main` after SoundCeiling v0.4.0.

**Goal:** Evolve SoundCeiling from one mostly stream-level normalizer into a capability-driven Hybrid Engine that can apply safe global control everywhere, smarter PCM-aware control where Android permits it, per-app and system-sound policies, and device-specific limits without claiming capabilities the platform cannot prove.

## 1. Non-negotiable principles

1. **Safety before normalization.** A requested raise may happen only when the engine has enough trustworthy information to justify it.
2. **No confidence, no raise.** Ambiguous source identity, blocked/uncertain PCM, mixed sources that cannot be isolated, or an unhealthy backend disables automatic upward control.
3. **Manual user intent outranks automation.** Existing v0.4 manual-pause/effective-envelope behavior remains authoritative.
4. **Safety Lock is final.** Existing `SafetyGuard` and `SafeVolumeController` remain the final ordinary Media write path.
5. **No fake DSP.** PCM capture is analysis, not proof that SoundCeiling can replace the original app audio with processed PCM.
6. **Optional subsystems fail closed.** Per-app source detection, OEM integration, DSP effects and future privileged transports may degrade independently without disabling the core safety guard.
7. **Microphone isolation.** Production analysis code must never switch to microphone/voice audio sources.
8. **No root requirement for Standard Engine.** Root/Shizuku/OEM privileged paths are future adapters, not prerequisites for v0.5 core behavior.

## 2. Scope

### In scope for v0.5

- Capability-driven engine model replacing the single linear backend tier as the authoritative representation.
- Playback activity observation.
- Source identity/confidence model.
- UID-filtered `AudioPlaybackCapture` infrastructure when a package UID is known and capture is permitted.
- PCM blocked/uncertain state machine.
- Per-app policy model: `GLOBAL`, `ON`, `OFF`, `CUSTOM`.
- Separate system-sound policies for Media, Calls, Alarm, Ringtone, Notifications and other supported streams.
- Samsung/system apps opt-in behavior, with sensitive Samsung apps disabled by default.
- Multi-source conflict resolution.
- Device Profiles 2.0 with per-output limits and migration from v0.4 calibration profiles.
- Expanded runtime status and diagnostics.
- Capability probes for per-app volume and DSP transport without pretending unsupported paths are active.
- UI for app/system rules, device profiles and engine confidence/status.

### Explicitly out of scope for v0.5 Standard Engine

- Root installation or root-only audio routing.
- A universal sample-level brickwall limiter for arbitrary third-party Android playback.
- Guaranteed per-app volume writes on stock Android when no verified API/transport exists.
- Automatic UI scripting of Samsung SoundAssistant as a safety-critical mechanism.
- Microphone, call-recording or voice-recording analysis.
- Google Play packaging/policy work.

## 3. Why the current architecture changes

`NormalizerService` in v0.4 owns too many responsibilities: MediaProjection setup, PCM reading, Visualizer fallback, route tracking, settings refresh, policy decisions, safety application, diagnostics, logging and notifications.

v0.5 keeps the Android foreground service as the lifecycle shell, but moves decisions into bounded components. The service must orchestrate components; it must not become the location where new source/app/device rules accumulate.

The old `AudioBackendStatus.Tier` may remain temporarily for migration/UI compatibility, but it is no longer sufficient as the engine's truth model because these capabilities are independent. For example, PCM metering may be available while per-app volume control and DSP transport are unavailable.

## 4. Capability model

Introduce a single immutable `EngineCapabilities` snapshot with independent dimensions.

### 4.1 Playback observation

`PlaybackObservationCapability`

- `AVAILABLE`
- `DEGRADED`
- `UNAVAILABLE`

Purpose: determine whether playback is believed to be active and provide non-PCM evidence for blocked-capture detection.

### 4.2 Source identity

`SourceIdentityConfidence`

- `EXACT` — one package/UID is resolved with sufficient evidence.
- `LIKELY` — one source is likely but not guaranteed.
- `MIXED` — multiple active sources are known or strongly indicated.
- `UNKNOWN` — source cannot be assigned safely.

Only `EXACT` may enable source-specific automatic upward control.

### 4.3 Metering

`MeteringCapability`

- `PCM_EXACT` — capture filtered to the intended known UID/source and producing valid PCM.
- `PCM_MIXED` — valid PCM is available but may contain multiple sources.
- `OUTPUT_MIX_PEAK_RMS` — global output-mix Peak/RMS only.
- `ACTIVITY_ONLY` — playback activity is known but no trustworthy level measurement exists.
- `NONE`.

### 4.4 Volume control

`VolumeControlCapability`

- `PER_APP_VERIFIED` — only when a concrete verified implementation exists.
- `STREAM_MEDIA` — stock Media stream index control.
- `SYSTEM_STREAMS` — selected Android stream controls explicitly enabled by the user.
- `NONE`.

`PER_APP_VERIFIED` must not be reported merely because an app UID is known.

### 4.5 DSP transport

`DspTransportCapability`

- `VERIFIED_GLOBAL`
- `VERIFIED_SOURCE`
- `EXPERIMENTAL`
- `UNAVAILABLE`

DSP UI may expose experimental capability, but the core engine must label it separately from verified transport.

## 5. Engine components

### 5.1 `PlaybackObserver`

Responsibilities:
- observe whether playback is active;
- collect public Android playback metadata that is actually available;
- publish time-stamped observations;
- never infer an exact package solely from weak metadata.

Output: `PlaybackSnapshot`.

### 5.2 `SourceResolver`

Responsibilities:
- combine app policy configuration, known package-to-UID mapping, playback observations and capture results;
- produce `SourceSet` plus `SourceIdentityConfidence`;
- distinguish exact, likely, mixed and unknown states;
- never upgrade `LIKELY` to `EXACT` without a verifiable signal.

Package name is the durable app identity. UID is runtime metadata and must be re-resolved after package changes.

### 5.3 `PcmCaptureBackend`

Responsibilities:
- create MediaProjection/AudioPlaybackCapture capture sessions;
- optionally filter by a resolved UID;
- expose PCM frames and capture health;
- distinguish "no samples because nothing is playing" from a capture error only when corroborating evidence exists;
- never use microphone sources.

No DSP write-back is implied by this backend.

### 5.4 `MeteringEngine`

Responsibilities:
- reuse v0.4 `LoudnessMeter`, raw block peak measurement, `PeakSafetyDetector`, `TransientGuard`, RMS/LUFS-like tracking and frequency diagnostics;
- attach confidence/source metadata to each measurement;
- expose whether a measurement may justify downward-only or bidirectional normalization.

### 5.5 `CapabilityResolver`

Responsibilities:
- build `EngineCapabilities` from backend health, source confidence, PCM state, verified control adapters and DSP adapters;
- publish a human-readable reason for every downgrade;
- choose no-raise behavior whenever required capability evidence disappears.

### 5.6 `PolicyResolver`

Responsibilities:
- resolve global settings + device profile + app rule + system-stream rule into one `EffectivePolicy`;
- perform no Android writes;
- encode conservative multi-source precedence rules;
- preserve Safety Lock and manual envelope as independent final constraints.

### 5.7 `ControlExecutor`

Responsibilities:
- choose the verified control adapter permitted by `EffectivePolicy` and capabilities;
- ordinary Media writes continue through `SafeVolumeController`;
- system-stream writes use a separate explicitly permissioned path and never share Media normalization state accidentally;
- unverified per-app adapters may not execute writes.

### 5.8 `DeviceProfileResolver`

Responsibilities:
- identify active output route;
- load or create the matching Device Profile 2.0;
- supply calibration, per-stream limits and device-specific app overrides;
- fall back to conservative defaults if the route/profile is uncertain.

### 5.9 `DspTransport`

Interface only in Standard Engine unless a verified implementation exists.

Responsibilities:
- report transport capability and scope;
- accept a future processing graph only when it can actually affect the relevant output;
- never mark DSP active from successful PCM capture alone.

Future adapters may include OEM, Shizuku or root implementations without changing `PolicyResolver`.

## 6. Runtime data model

### 6.1 `PlaybackSnapshot`

Minimum fields:
- `active`
- `observedUsages`
- `observedPlayers`
- `updatedElapsedMs`
- `observerHealth`

No field named `uid` or `packageName` should be populated unless the implementation can support that claim.

### 6.2 `SourceDescriptor`

- `packageName`
- `uid`
- `displayName`
- `systemApp`
- `samsungApp`
- `sensitiveDefaultOff`

The package name is persistence identity; UID is refreshed runtime identity.

### 6.3 `SourceSet`

- zero, one or many `SourceDescriptor`s
- `SourceIdentityConfidence`
- evidence/reason code

### 6.4 `MeasurementSnapshot`

- `MeteringCapability`
- `signalPresent`
- raw peak dBFS
- RMS dBFS
- LUFS-like
- transient delta
- source set
- measurement age
- trusted for downward control
- trusted for upward control

### 6.5 `EffectivePolicy`

At minimum:
- control enabled
- allow automatic raise
- allow automatic decrease
- Media min/max
- Safety Lock state/index
- normalization preset/strength/target
- peak threshold
- transient thresholds
- system stream and stream ceiling, if applicable
- active app rule and source of inheritance
- device profile key
- fallback ceiling

## 7. Per-app policies

Each installed app may have one rule.

### `GLOBAL`
Inherit global Media behavior and device overrides.

### `ON`
Participate in SoundCeiling using global/default parameters unless a device override supplies stricter limits.

### `OFF`
SoundCeiling must not perform app-specific normalization for this app.

If the app is mixed with another source and SoundCeiling has only global Media stream control, `OFF` prevents source-specific automatic changes that could alter that app. A separately configured global Safety Lock may still clamp Media because it is explicitly global safety behavior.

### `CUSTOM`
May override:
- comfort/target loudness;
- Media ceiling;
- normalization preset/strength;
- source peak threshold;
- transient protection;
- fallback ceiling;
- DSP preference;
- optional per-device overrides.

Custom app settings never bypass global Safety Lock.

## 8. App discovery and persistence

- Installed package name is the stable key.
- UID is resolved on demand and updated after install/update/reinstall events.
- Removed apps retain no active runtime UID.
- Search supports application label and package name.
- System and Samsung apps can be shown behind an explicit filter/toggle.
- Sensitive Samsung/system apps are default `OFF` until the user opts in.

Initial default-sensitive examples include Samsung Gallery and other Samsung/system apps selected by a conservative allowlist/denylist policy. The exact list must live in one versioned policy class, not scattered UI conditions.

## 9. System sounds policy

System streams are a separate domain from app policies.

Default v0.5 state:
- Media: `ON` using normal SoundCeiling behavior.
- Calls: `OFF`.
- Alarm: `OFF`.
- Ringtone: `OFF`.
- Notifications: `OFF`.
- Other supported system streams: `OFF` unless explicitly enabled.

When a user enables a system stream, they may configure a ceiling for that stream. Smart PCM normalization is not assumed for call/alarm/ringtone/notification streams.

The system-stream controller must never silently become enabled because an app rule was enabled.

## 10. PCM state machine

Introduce `PcmAvailabilityState`:

- `IDLE` — no convincing playback activity.
- `STARTING` — capture is being established.
- `ACTIVE` — valid PCM measurements are arriving.
- `SILENT_SOURCE` — capture is healthy and source legitimately appears silent.
- `BLOCKED` — playback is corroborated externally but intended PCM remains unavailable long enough to satisfy the blocked criterion.
- `UNCERTAIN` — evidence is insufficient to classify blocked vs silent vs unrelated playback.
- `ERROR` — capture backend failed.

### Blocked criterion

`BLOCKED` may be entered only when all are true:
1. playback activity is currently corroborated;
2. capture health itself is not simply stopped by the user;
3. expected source/usage is eligible for the attempted capture path;
4. no valid PCM arrives for a bounded interval;
5. at least one independent signal indicates audio activity, or exact source activity is otherwise proven.

If any requirement is missing, use `UNCERTAIN`, not `BLOCKED`.

### Safety behavior by state

- `ACTIVE` + exact source + healthy policy: bidirectional normalization may be allowed.
- `ACTIVE` but mixed/unknown source: downward protection allowed; automatic raise blocked.
- `BLOCKED`: no automatic raise; fallback ceiling may decrease Media if explicitly configured.
- `UNCERTAIN`: no automatic raise.
- `ERROR`: no automatic raise; retain core Safety Lock/Media guard.
- `IDLE`: do not chase volume.

## 11. Multi-source conflict resolution

When multiple sources are active and SoundCeiling cannot independently control each source, use deterministic conservative rules.

1. Global Safety Lock always applies.
2. Any exact `OFF` source blocks source-specific automatic stream changes that would affect it.
3. Any ambiguous or mixed source set blocks automatic raise.
4. For downward ceilings, the strictest applicable explicitly enabled safety ceiling wins.
5. App-specific comfort normalization may run only when the relevant source is exact or a verified per-app control adapter isolates it.
6. A source with `CUSTOM` never weakens a stricter device/global safety ceiling.
7. A source transition resets upward-release timing so a newly started quiet app cannot immediately trigger a raise while another source may still be audible.

Example: a quiet Telegram clip plus a loud game with only global Media control results in no automatic raise. If both app policies permit SoundCeiling and one has a stricter safety ceiling, only a safe downward clamp may occur.

## 12. Device Profiles 2.0

Replace the narrow v0.4 calibration-only profile with a versioned profile that keeps old calibration data.

Minimum fields:
- stable route/profile key;
- display name;
- Android device type/product metadata;
- calibration offset;
- Media ceiling;
- optional per-system-stream ceilings;
- fallback ceiling when PCM is unavailable;
- last selected control profile;
- per-app override map;
- migration/version metadata;
- updated timestamp.

### Migration

- Existing v0.4 `DeviceProfile` entries are imported without losing calibration offsets.
- Missing new fields receive current conservative defaults.
- Migration is idempotent.
- Corrupt individual entries are skipped/recoverable without disabling the engine.
- A migrated profile must not automatically enable Calls/Alarm/Ringtone/Notifications.

## 13. Microphone isolation contract

The app still may require Android's `RECORD_AUDIO` permission for playback-analysis APIs, but SoundCeiling production analysis must not record physical microphone or voice sources.

CI/source invariant must fail if production engine code introduces:
- `MediaRecorder.AudioSource.MIC`;
- `MediaRecorder.AudioSource.VOICE_COMMUNICATION`;
- `MediaRecorder.AudioSource.VOICE_CALL` or related call sources;
- `AudioRecord.Builder.setAudioSource(...)` in the playback-analysis path.

`PcmCaptureBackend` must use playback capture configuration, never microphone-source configuration.

Camera, recorder and voice-call microphone ownership remains outside SoundCeiling.

## 14. Samsung and OEM behavior

- Samsung/system apps that could have sensitive media/camera/gallery/communication behavior default to SoundCeiling app-policy `OFF` until explicitly enabled.
- Outgoing Media playback may be controlled only according to explicit app/system policy.
- No OEM automation is considered safety-critical unless its API/transport is programmatically verified.
- SoundAssistant UI automation is not part of Standard Engine.
- A future `PerAppVolumeController` OEM adapter must report `PER_APP_VERIFIED` only after a capability probe succeeds for the actual device.

## 15. DSP architecture

### Standard Engine v0.5

Keeps the existing v0.4 volume-level safety/normalization core and exposes DSP capability truthfully.

Possible UI states:
- DSP unavailable;
- DSP experimental;
- DSP verified for this source/output.

No EQ/compressor/limiter control may claim to protect global third-party playback unless `DspTransportCapability` is verified for that scope.

### Future Deep DSP Engine

When a privileged or OEM transport can actually intercept/replace output, the intended graph is:

`input PCM -> normalization gain -> EQ -> multiband compressor -> look-ahead peak stage -> true-peak/brickwall limiter -> output`

That future graph must still consume the same app/device policy and Safety Lock concepts. Root/Shizuku code must live behind adapters rather than in the standard policy layer.

## 16. UI design

Add an **Apps & system sounds** destination.

### Apps section
- search by app label/package;
- filter user apps / system apps / Samsung apps;
- each row shows `Global`, `On`, `Off`, or `Custom`;
- sensitive default-off apps visibly indicate that they require opt-in;
- Custom opens app-specific controls;
- device-specific override is optional and visually separate from global app settings.

### System sounds section
Separate rows for Media, Calls, Alarm, Ringtone, Notifications and supported additional streams. Each non-Media row defaults disabled and shows its own ceiling only when enabled.

### Engine status
Simple mode should show a short current status such as:
- `Smart PCM`;
- `PCM blocked - safe fallback`;
- `Mixed apps - raise paused`;
- `Waiting for audio`;
- `Safe fallback`;
- `System limiter only`;
- `DSP active` only when verified.

Advanced/Diagnostics shows the independent capability dimensions and downgrade reasons.

## 17. Diagnostics and logging

Extend v0.4 black-box logs without recording PCM.

New event classes include:
- playback activity start/stop;
- source confidence transitions;
- package/UID resolution changes;
- PCM state transitions;
- capability upgrades/downgrades;
- per-app policy resolution;
- multi-source conflict decisions;
- system-stream control decisions;
- device profile migration/switch;
- attempted use of unsupported per-app/DSP adapter;
- raise-block reason.

Suggested diagnostic codes:
- `source_unknown`;
- `source_mixed`;
- `pcm_blocked`;
- `pcm_uncertain`;
- `per_app_control_unavailable`;
- `dsp_transport_unverified`;
- `system_stream_disabled`;
- `policy_conflict_off_source`;
- `device_profile_fallback`.

Repeated stable states should be deduplicated to protect the existing bounded log budget.

## 18. Safety and control precedence

For ordinary Media, final precedence is:

1. user manual intent / manual safety pause;
2. explicit app/system `OFF` constraints that prohibit source-specific automation;
3. capability confidence, especially the no-raise rule;
4. emergency raw peak/transient downward request;
5. normalization request;
6. strictest applicable app/device/global ceiling;
7. Safety Lock;
8. `SafeVolumeController` -> `VolumeApplier`.

No new component may call `AudioManager.setStreamVolume(STREAM_MUSIC, ...)` directly.

System-stream writes are separate and must be limited to their explicitly enabled stream policy.

## 19. Backward compatibility

- v0.4 Simple/Advanced settings remain readable.
- v0.4 manual-pause behavior remains.
- v0.4 Safety Lock remains off by default and final when enabled.
- v0.4 LUFS-like/peak/transient behavior is reused rather than rewritten unless tests prove a required change.
- Existing log retention behavior remains bounded.
- Existing calibration offsets survive Device Profile 2.0 migration.
- Existing MediaProjection permission flow remains the precision PCM entry point.

## 20. Testing requirements

### Pure tests

Must cover:
- capability resolver combinations;
- exact/likely/mixed/unknown source confidence;
- no auto-raise for mixed/unknown/blocked/uncertain/error states;
- app rule inheritance and Custom overrides;
- `OFF` source conflict behavior;
- strictest ceiling wins;
- source-transition upward hold;
- system streams default off;
- Device Profile 2.0 migration/idempotence;
- UID refresh model after package change;
- fallback ceiling behavior;
- verified vs unverified DSP/per-app control states.

### Source invariants

CI must reject:
- new ordinary Media `setStreamVolume` callers outside the approved writer path;
- microphone/call audio-source use in production analysis;
- code that marks `PER_APP_VERIFIED` or verified DSP without going through a capability adapter/probe;
- automatic-raise paths that bypass the capability/policy no-raise gate.

### Android integration tests/checks

Where practical, verify:
- app list/search/persistence;
- package UID resolution;
- MediaProjection/UID-filter configuration construction;
- system-stream mapping and defaults;
- route/profile switching;
- runtime-state rendering.

### Regression gates

All v0.4 pure tests and source/UI/package contracts remain green unless a contract is intentionally versioned with an equivalent replacement.

## 21. Release acceptance criteria

v0.5 is releasable only when all are true:

1. Standard Engine works with no root.
2. Core Media SafetyGuard cannot be bypassed by new app/device logic.
3. Automatic raise is impossible in `MIXED`, `UNKNOWN`, `BLOCKED`, `UNCERTAIN` or unhealthy measurement states.
4. Calls, Alarm, Ringtone and Notifications remain disabled by default.
5. Sensitive Samsung/system apps remain app-policy `OFF` by default until user opt-in.
6. App policy persists by package name, not permanent UID.
7. Device Profile 2.0 migration preserves old calibration data.
8. Production analysis contains no microphone/call audio source.
9. Unsupported per-app or DSP capabilities are reported as unavailable, not simulated.
10. Existing v0.4 tests plus new v0.5 gates pass.
11. `assembleDebug` succeeds and the artifact checksum is verified before merge.

## 22. Planned implementation boundary

The implementation should be decomposed so that the first v0.5 release can ship before any privileged Deep DSP work.

Expected first-release layers:

1. capability/source/policy pure models;
2. app discovery and policy persistence;
3. system-stream policy model;
4. Device Profiles 2.0 migration;
5. playback observer + PCM confidence state machine;
6. UID-filtered capture infrastructure;
7. conservative multi-source resolver;
8. refactored service orchestration;
9. Apps & system sounds UI;
10. diagnostics and release gates.

Future Deep DSP adapters are separate follow-up projects behind the interfaces defined here.

## 23. API reality assumptions to preserve

The implementation must remain conservative around Android public API limits:

- playback capture availability does not imply every third-party stream is capturable;
- knowing an installed package UID does not prove that package is the currently audible source;
- public playback observation metadata must not be treated as guaranteed exact source identity unless the platform actually provides sufficient evidence;
- PCM analysis does not itself provide a path to replace another app's playback;
- global/per-app DSP status must reflect verified transport, not merely successful effect construction or capture.

If platform research later proves a stronger capability on a specific Android/OEM version, add it as a capability adapter rather than weakening these baseline rules.
